# 校园活动管理系统 — 学生访谈需求分析

> 访谈对象：使用校园活动管理系统的学生（活动参与者）  
> 访谈方式：开放式问答  
> 分析目的：从学生实际使用视角验证 V1.0 功能缺口，确认 V2.0 需求优先级与实现方向。

---

## 一、访谈核心信息提取

### 1.1 热门活动满员后缺少候补机会

| 学生原话 | 解读 |
|---|---|
| “有些热门活动确实很快就满了，我稍微晚一点看到，基本就报不上了。” | 容量制活动先到先得，满员后系统直接拒绝报名，学生没有表达继续参与意愿的渠道。 |
| “现在满了以后我基本只能放弃。就算后来有人不参加，我也不太清楚自己还能不能补进去。” | 名额释放没有透明机制，学生不知道存在候补递补的可能。 |
| “如果活动满了，我愿意先等一等，也希望知道自己是不是还在等待。” | 学生接受排队机制，但前提是能明确知道自己是否在候补队列及当前位置。 |

**现有 V1.0 状态**：满员即报名失败，无候补功能。

---

### 1.2 报名后状态不透明

| 学生原话 | 解读 |
|---|---|
| “普通活动一般比较直接，但有些活动提交以后不能马上确定能不能参加，我有时看不明白自己现在是什么情况。” | 部分活动需要审核或排队，但学生看不到“审核中 / 已通过 / 候补 / 已拒绝”等细分状态。 |
| “我只知道有些活动提交以后要等组织活动的老师确认，具体按什么条件判断，我并不清楚。” | 活动详情缺少参与条件说明，学生不知道审核标准。 |

**现有 V1.0 状态**：学生只能看到“已报名 / 未报名”，没有细分状态，也缺少参与条件展示。

---

### 1.3 临时无法参加时希望释放名额

| 学生原话 | 解读 |
|---|---|
| “有时候报名以后临时有事确实去不了，我希望能把自己的报名处理掉，而不是一直占着位置。” | 学生有主动取消报名的需求，以便把名额让给其他人。 |

**现有 V1.0 状态**：已支持学生取消报名（OPEN 状态下），但入口和状态反馈可以更加明显。

---

### 1.4 对候补顺序的认知

| 学生原话 | 解读 |
|---|---|
| “你觉得应该按什么顺序决定谁先补进去？先报名的先补吗？” | 学生默认“先到先得”是公平规则，但也希望规则由教师明确说明。 |
| “具体顺序怎么定，我只知道应该由活动老师说明。” | 候补规则需要在活动参与条件或详情页中明确告知。 |

**现有 V1.0 状态**：无候补机制，也无相关规则说明。

## 二、学生痛点 → V2.0 候选需求映射

| 痛点编号 | 学生痛点 | 对应 V2.0 需求 | 当前实现状态 |
|---|---|---|---|
| P1 | 热门活动满员后报不上，只能放弃 | FR10 候补报名 | ✅ 已支持：满员后学生可加入候补队列（WAITING） |
| P2 | 不知道是否还有机会补进去 | FR12 学生查看报名状态 | ✅ 已支持：活动详情页与“我的报名”展示候补状态 |
| P3 | 提交后不确定能否参加 | FR9 报名审核 + FR12 状态可见 | ✅ 已支持：教师可审核，学生可见“审核中 / 已通过 / 已拒绝” |
| P4 | 临时有事想取消报名 | V1.0 取消报名（可继续优化入口） | ✅ 已支持：学生可在“我的报名”或活动详情页取消 |
| P5 | 有人退出后自己能否补进不清晰 | FR11 候补自动递补 + FR12 状态可见 | ✅ 已支持：取消时自动从候补队列按时间顺序转正 |
| P6 | 不知道教师按什么条件审核 | FR8 参与条件说明 | ✅ 已支持：活动新增 requirements 字段并在详情页展示 |
| P7 | 希望知道候补顺序及规则 | FR12/FR14 状态可见 + FR8 条件说明 | ✅ 已支持：展示“候补第 N 位”；规则需教师填写到 requirements |

## 三、V2.0 实现对学生痛点的覆盖评估

| 需求 | 覆盖的痛点 | 实现要点 | 仍待优化 |
|---|---|---|---|
| FR8 参与条件说明 | P6、P7 | Activity 新增 requirements 字段，详情页展示 | 发布时可提示教师说明“审核条件、候补规则” |
| FR9 报名审核 | P3 | 报名后状态为 PENDING，教师 approve/reject | 教师审核后学生应及时收到状态变化反馈 |
| FR10 候补报名 | P1、P2 | 满员后若 allowWaitlist=true，学生进入 WAITING | 热门活动默认开启候补是否更合适？ |
| FR11 候补自动递补 | P2、P5 | 取消报名时按 waitingNo 最小者转正 | 候补转正可考虑发送通知 |
| FR12/FR14 状态可见 | P2、P3、P5、P7 | 详情页与我的报名页展示状态 | 列表页可展示“可候补 / 需审核”标签 |
| FR13 活动编辑 | - | 教师可编辑 OPEN 活动 | 编辑后应通知已报名学生 |
| FR15 报名截止时间 | - | 超过 deadline 后禁止报名 | 列表与详情页增加倒计时/已截止提示 |

## 四、对现有界面的优化建议

### 4.1 活动详情页

- 明确展示“参与条件 / 审核标准”字段（requirements）。
- 当活动满员但开启候补时，按钮文案由“立即报名”改为“加入候补”。
- 学生报名后，在详情页顶部显示当前状态卡片：审核中 / 已通过 / 候补第 N 位 / 已拒绝。

### 4.2 我的报名页

- 增加状态颜色标签：
  - 审核中：黄色
  - 已报名 / 已通过：绿色
  - 候补：蓝色（显示“候补第 N 位”）
  - 已拒绝 / 已取消：灰色/红色
- 对“候补”状态的记录增加提示文案：“如果有人取消，您将按候补顺序自动转正。”

### 4.3 活动列表页

- 增加标签：
  - “需审核”
  - “可候补”
  - “已截止”
- 已满员但可候补的活动显示“可候补”而不是直接隐藏或禁用。

### 4.4 教师活动管理页

- 编辑按钮旁增加提示：仅 OPEN 状态可编辑。
- 名单页增加“候补队列”单独分组，便于教师查看。

## 五、验证建议（M6 用户访谈验证）

可针对本次访谈中学生提到的痛点设计以下验收场景：

| 场景编号 | 验证内容 | 预期结果 |
|---|---|---|
| S7 | 学生报名需要审核的活动 | 报名后状态为“审核中”，教师通过前状态不变 |
| S8 | 学生查看自己的报名状态 | “我的报名”页能看到审核中 / 已报名 / 候补第 N / 已拒绝 |
| S9 | 热门活动满员后学生候补 | 满员后显示“加入候补”，加入后状态为“候补第 N 位” |
| S10 | 候补学生自动转正 | 已报名学生取消后，候补第 1 位自动变为“已报名” |
| S11 | 学生查看参与条件 | 活动详情页能看到教师填写的参与条件 / 审核规则 |
| S12 | 学生主动取消报名 | 在我的报名页可取消，取消后名额释放给候补 |

## 六、与教师访谈的交叉验证结论

| 维度 | 教师视角 | 学生视角 | 一致性 |
|---|---|---|---|
| 报名审核 | 需要按条件筛选参与者 | 希望知道审核标准和结果 | ✅ 双方都认为需要 |
| 候补机制 | 满员后保留候补名单，自动递补 | 愿意候补，但需要知道自己在队列中的位置 | ✅ 一致 |
| 状态可见 | 教师要分清正式/候补/审核中 | 学生要看懂自己的状态 | ✅ 一致 |
| 活动编辑 | 教师需要修改活动信息 | 学生希望信息准确 | ✅ 一致 |
| 取消报名 | 学生取消后名额应释放给候补 | 愿意主动取消，不占位置 | ✅ 一致 |

**结论**：V2.0 已实现的 FR8–FR15 覆盖了教师与学生双方访谈中识别出的核心痛点。后续重点是界面提示与反馈的优化，以及是否需要增加消息通知机制。
