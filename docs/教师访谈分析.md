# 校园活动管理系统 — 教师访谈需求分析

> 访谈对象：活动组织教师  
> 访谈方式：开放式问答  
> 分析目的：从真实使用者视角补充、验证 V1.0 需求，识别下一轮迭代（V1.x / V2.0）的候选功能。

---

## 一、访谈核心信息提取

### 1.1 报名不等于参加：需要“资格审核”

| 教师原话 | 解读 |
|---|---|
| “没通过说明不符合这次活动的参加条件；通过以后还要看当时有没有位置，并不代表一定已经正式参加。” | 报名后需要教师审核，审核通过才获得参与资格；通过仅代表“符合条件”，还要结合容量判断最终是否正式参加。 |
| “我只处理自己负责活动的申请，会按这个活动已经说明的条件确认通过或拒绝。” | 审核是按活动维度隔离的，由发布教师操作，审核依据是活动说明中的参与条件。 |

**现有 V1.0 状态**：学生报名即成功，没有“审核中 / 已通过 / 已拒绝”状态。

---

### 1.2 容量满员后需要“候补名单”

| 教师原话 | 解读 |
|---|---|
| “活动已经满员时，可以先保留这些仍想参加的学生，让他们处在候补中。” | 当报名人数 ≥ 容量时，后续报名学生进入候补队列，而不是直接拒绝。 |
| “已经确定参加的学生取消后，正式人数会少一人，也就空出一个位置。” | 取消会释放名额，候补学生可递补为正式参加。 |
| “那接下来的候补名单是不是会正常递补” | 教师期望系统自动或半自动完成候补→正式的递补。 |

**现有 V1.0 状态**：满员后直接拒绝报名，没有候补机制。

---

### 1.3 学生需要看到自己的报名状态

| 教师原话 | 解读 |
|---|---|
| “我得分清哪些人已经确定参加、哪些人还在候补，学生本人也应该能看明白自己的情况。” | 学生端需要明确展示当前状态：审核中 / 已通过（候补） / 已正式参加 / 已拒绝 / 已取消。 |

**现有 V1.0 状态**：学生只能看到“已报名 / 未报名”，没有细分状态。

---

### 1.4 活动信息可能变化，教师需要及时修改

| 教师原话 | 解读 |
|---|---|
| “我负责的活动由我创建和发布，时间、地点等信息有变化时，也应由我及时调整。” | 教师拥有活动信息的修改权，包括时间、地点、容量、参与条件等。 |
| “不同活动不一样，我会根据场地、设备和组织条件，确定自己负责的活动最多能接待多少人。” | 容量不是固定规则，而是按活动单独设置，且可能因场地/设备变化而调整。 |

**现有 V1.0 状态**：活动发布后仅支持“结束 / 取消”，不支持编辑修改。

---

### 1.5 学生可主动取消报名

| 教师原话 | 解读 |
|---|---|
| “学生临时不能参加时，可以取消自己的报名，最好尽早处理，让名单保持准确。” | 学生应有取消报名入口；取消后名额可释放给候补同学。 |

**现有 V1.0 状态**：已支持学生取消报名（OPEN 状态下）。

## 二、V1.0 已覆盖 vs 未覆盖对照

| 需求点 | V1.0 支持情况 | 访谈中暴露的缺口 |
|---|---|---|
| 用户注册 / 登录 / 角色分流 | ✅ 已支持 | 无 |
| 教师发布活动 | ✅ 已支持 | 缺少“参与条件”字段 |
| 学生浏览活动 | ✅ 已支持 | 缺少状态细分展示 |
| 学生报名 / 取消 | ✅ 已支持 | 报名即成功，缺少审核与候补 |
| 教师查看名单 | ✅ 已支持 | 名单缺少“正式 / 候补 / 审核中”分组 |
| 教师结束 / 取消活动 | ✅ 已支持 | 缺少“编辑修改活动信息” |
| 资格审核 | ❌ 未支持 | 核心缺口 |
| 候补机制 | ❌ 未支持 | 核心缺口 |
| 报名状态可见性 | ❌ 未支持（仅已报名/未报名） | 核心缺口 |
| 活动时间 / 地点变更 | ❌ 未支持 | 重要缺口 |
| 报名截止时间 | ❌ 未支持 | 访谈未直接提及，但与审核、状态流转相关 |

## 三、新增候选需求清单（供 V1.x / V2.0 评审）

### 3.1 功能需求

| 编号 | 需求 | 说明 | 建议阶段 |
|---|---|---|---|
| FR8 | 活动参与条件说明 | 发布活动时填写参与条件（如年级、专业、先修要求等），作为审核依据 | V2.0 |
| FR9 | 报名资格审核 | 教师对学生报名进行“通过 / 拒绝”，学生状态变为“已通过”或“已拒绝” | V2.0 |
| FR10 | 候补报名 | 满员后学生可选择“候补”，进入候补队列 | V2.0 |
| FR11 | 候补自动递补 | 正式名额释放时，按报名时间顺序将候补学生递补为正式参加 | V2.0 |
| FR12 | 学生查看报名状态 | 学生可在“我的报名”中看到：审核中 / 已通过（候补） / 已正式参加 / 已拒绝 / 已取消 | V2.0 |
| FR13 | 教师编辑活动信息 | 教师在活动 OPEN 状态下可修改标题、时间、地点、容量、简介、参与条件 | V2.0 |
| FR14 | 教师管理报名状态 | 教师可在名单中标记学生为“正式参加”或移入候补 | V2.0 |
| FR15 | 报名截止时间 | 活动可设置报名截止时间与活动开始时间，截止后停止报名 | V2.0 可选 |

### 3.2 业务规则

| 编号 | 规则 | 说明 |
|---|---|---|
| BR6 | 报名需经教师审核 | 学生报名后状态为“审核中”，教师审核通过后进入“已通过” |
| BR7 | 通过审核不等于正式参加 | 已通过学生若当前正式人数 ≥ 容量，则进入“候补”状态 |
| BR8 | 候补按时间顺序递补 | 正式名额释放时，最早进入候补的学生优先递补 |
| BR9 | 容量可动态调整 | 教师可在活动 OPEN 状态下增加或减少容量；增加容量时按候补顺序递补，减少容量时最后一批正式参加学生可能降级为候补 |
| BR10 | 活动信息变更需同步 | 教师修改时间、地点等信息后，已报名学生应能看到最新信息 |
| BR11 | 取消报名释放名额 | 学生取消报名后，该活动正式人数减 1，候补学生按顺序递补 |

### 3.3 数据状态扩展

| 状态 | 含义 | 适用对象 |
|---|---|---|
| PENDING | 审核中 | 学生报名后等待教师审核 |
| APPROVED | 已通过（但未正式参加） | 教师审核通过，等待容量确认 |
| ENROLLED | 已正式参加 | 已通过且有可用名额 |
| WAITLIST | 候补中 | 已通过但当前无名额，或满员后报名 |
| REJECTED | 已拒绝 | 教师审核不通过 |
| CANCELLED | 已取消 | 学生主动取消 |

## 四、对现有系统的调整建议

如果小组决定将上述需求纳入下一版，现有数据表和活动流程需要以下调整：

### 4.1 数据表调整

1. **Activity 表**：
   - 新增字段 `requirements`（参与条件说明，文本）
   - 新增字段 `registrationDeadline`（报名截止时间，可选）

2. **Enrollment 表**：
   - 将现有状态隐含为“已报名”，改为显式字段 `status`（PENDING / APPROVED / ENROLLED / WAITLIST / REJECTED / CANCELLED）
   - 新增字段 `sequence`（报名顺序，用于候补递补）

3. **新增 Waitlist 表（可选）**：
   - 如果希望候补逻辑独立，可单独建表；但复用 Enrollment 表并增加状态字段更简洁。

### 4.2 流程调整

```
学生报名
  → 状态 = PENDING（审核中）
  → 教师审核：
       拒绝 → REJECTED
       通过 → 判断当前正式人数 < 容量？
              是 → ENROLLED
              否 → WAITLIST

学生 / 教师取消 / 名额释放
  → 正式人数减少
  → 从 WAITLIST 中按 sequence 最小者递补为 ENROLLED
```

### 4.3 页面调整

| 页面 | 调整内容 |
|---|---|
| 活动发布 / 编辑页 | 增加“参与条件”和“报名截止时间”输入框 |
| 活动详情页 | 学生看到自己当前报名状态；教师增加“审核报名”入口 |
| 教师报名名单页 | 增加状态筛选、通过/拒绝/标记候补按钮 |
| 我的报名页 | 展示状态：审核中 / 已通过（候补） / 已正式参加 / 已拒绝 / 已取消 |
| 活动管理页 | 增加“编辑活动”按钮 |

## 五、V2.0 工程意图草案（五问）

| 问题 | 回答 |
|---|---|
| 为什么要做这一版？ | V1.0 解决了“能不能报名”，但真实业务中报名不等于参加；V2.0 解决“谁能参加、谁候补、谁被拒绝”的精细化管理问题。 |
| 解决什么问题？ | ① 满员后学生无法表达参与意愿；② 教师无法按条件筛选参与者；③ 学生不知道自己到底是否正式参加；④ 活动信息变化后无法及时调整。 |
| 这一版做什么？ | 资格审核、候补机制、状态可见、活动信息编辑、候补自动递补。 |
| 约束是什么？ | 继续沿用 V1.0 技术栈；状态流转必须保证数据一致性；教师只能管理自己发布的活动。 |
| 怎么算完成？ | S7–S12 新增验收场景全部通过；现有 S1–S6 回归通过。 |

---

## 六、下一步建议

1. **小组评审本分析**：确认哪些需求进入 V2.0，哪些延后。
2. **更新需求分析文档**：把 FR8–FR15、BR6–BR11 加入正式需求。
3. **更新软件设计**：画出新的报名状态机图（PENDING → APPROVED → ENROLLED / WAITLIST）。
4. **规划数据迁移**：如果 V1.0 已有数据，需给旧报名记录一个默认状态（如 ENROLLED）。
5. **分步开发**：建议先实现“审核 + 状态可见”，再实现“候补 + 递补”，最后实现“活动编辑”。
