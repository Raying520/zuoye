## 二、业务背景分析

### 2.1 已确定的业务方向（来自任务书）

1. 系统需要支持**用户注册和登录**；
2. **学生**能够通过系统**了解和参与**校园活动；
3. **活动组织教师**能够通过系统**发布和管理**校园活动。

### 2.2 业务方向背后的现实问题（分析推断，需小组确认）

| 现状痛点 | 具体表现 | 系统应对 |
|---|---|---|
| 信息分散 | 活动靠海报、群通知传播，学生"不知道有什么活动" | 统一的活动发布与浏览入口 |
| 报名无序 | 报名靠表格、问卷、现场登记，组织者难以统计 | 统一的报名记录与人数统计 |
| 记录缺失 | 谁参加了什么活动，无据可查 | 报名记录持久化，学生可查"我的参与" |

**归结为两个核心问题**：
- **信息触达** —— 让学生方便地看到活动信息；
- **报名管理** —— 让组织者方便地收集、查看报名。

### 2.3 三个业务方向蕴含的系统含义

| 业务方向 | 推导出的系统要素 |
|---|---|
| 支持注册登录 | 存在**用户**，且必须**区分角色**（否则无法区分谁可发布、谁可报名） |
| 学生了解和参与 | 需要**活动展示**（列表 + 详情）和**参与通道**（报名） |
| 教师发布和管理 | 需要**活动的创建、修改、取消/结束**，以及**报名情况查看** |

## 三、用户与目标分析

| 用户 | 核心目标 | 关注点 | V1.0 处理方式 |
|---|---|---|---|
| **学生**（参与者） | 发现并参加感兴趣的活动；查看自己的参与情况 | 信息准确及时、报名方便、能否取消 | 提供浏览、报名、个人记录功能 |
| **组织教师**（组织者） | 高效发布活动；掌握报名动态 | 发布简单、名单清晰、可修改可取消 | 提供发布、管理、名单查看功能 |
| 系统管理员（隐含） | 管理用户账号 | 用户治理 | **V1.0 不设**，注册即用（在工程意图中声明此简化） |

**角色判定方式**：注册时选择身份（学生 / 教师）。V1.0 不做教师身份审核，作为**已知简化**明确声明。

---

## 四、基本业务过程（核心闭环）

```
注册/登录（选择角色）
   ├─ 教师侧：发布活动 → 管理活动（编辑/取消/结束）→ 查看报名名单
   └─ 学生侧：浏览活动 → 查看详情 → 报名/取消 → 查看我的参与
```

**该闭环是 V1.0 必须成立的最小业务过程**：教师发布 → 学生看到 → 学生报名 → 教师看到名单 → 活动结束 → 学生可回看记录。缺任何一环，基本业务即不成立。

## 五、候选需求清单

### 5.1 功能需求（核心，建议 V1.0 必做）

| 编号 | 需求 | 说明 |
|---|---|---|
| FR1 | 用户注册 | 填写账号、密码、姓名，选择角色（学生/教师） |
| FR2 | 用户登录/退出 | 按角色进入对应视图（学生看不到发布入口） |
| FR3 | 活动发布（教师） | 填写标题、简介、时间、地点、容量上限 |
| FR4 | 活动浏览（学生） | 活动列表 + 活动详情页 |
| FR5 | 活动报名/取消（学生） | 受容量、重复、活动状态约束 |
| FR6 | 报名名单查看（教师） | 查看某活动的报名学生列表和当前人数 |
| FR7 | 活动管理（教师） | 编辑活动信息；取消或结束活动 |

### 5.2 业务规则

| 编号 | 规则 |
|---|---|
| BR1 | 只有教师角色可以发布、编辑、取消活动 |
| BR2 | 学生只能报名"报名中"状态的活动 |
| BR3 | 报名人数达到容量上限后不可再报名 |
| BR4 | 同一学生对同一活动不可重复报名 |
| BR5 | 活动被取消或结束后，报名通道关闭（已产生的报名记录保留） |

### 5.3 数据需求

| 实体 | 关键字段 |
|---|---|
| 用户 User | id、账号、密码（**必须哈希存储**）、姓名、角色（student/teacher） |
| 活动 Activity | id、标题、简介、时间、地点、容量上限、状态（报名中/已结束/已取消）、发布教师 id |
| 报名记录 Enrollment | id、活动 id、学生 id、报名时间 |

**实体关系**：教师 1—n 活动；活动 1—n 报名记录；学生 1—n 报名记录。

### 5.4 非功能需求与约束

- **可用性**：核心操作（发布 → 报名 → 查看名单）无需培训即可完成；
- **安全**：密码不得明文存储；**仓库中不得提交密码、Token、密钥等敏感信息**（实验明确要求）；
- **规模**：按单机/小规模用户设计，不要求高并发；
- **时间**：9 月 13 日截止，技术栈应选择小组最熟悉的（如 Flask / Express + SQLite + 简单前端）。

### 5.5 扩展候选（可选，不建议为凑数实现）

活动搜索/筛选、活动签到、活动评价、消息通知、数据统计（报名率等）。

> 实验原则："在保证基本业务能够成立的基础上，可以根据本组分析结果完成其他合理内容，但**不要求为了增加功能数量而扩大系统范围**。"

## 六、工程意图（草案，供小组确认）

按任务书要求，工程意图需回答五个问题，以下是建议答案：

1. **为什么建设当前版本？**
   用最小可行版本验证"教师发布 — 学生参与"这一基本业务闭环能否信息化成立，为后续迭代打基础。

2. **当前版本主要解决什么问题？**
   活动信息分散、报名管理低效：让活动信息有统一的发布和浏览入口，让报名有统一的记录和统计。

3. **本轮准备完成哪些内容？**
   FR1–FR7 共 7 项核心功能、3 张数据表、5 条业务规则；不做管理员、身份审核、通知等扩展。

4. **软件实现需要遵守哪些重要约束？**
   2 学时 + 3 人以内 + 9 月 13 日截止；技术栈从简；密码哈希、不提交敏感信息；Git 从项目初期建立、随开发小步提交。

5. **根据什么判断当前版本已经达到预期目标？**
   第七节验收场景全部通过，即认为 V1.0 达标。

## 七、验证思路（验收标准草案）

**场景化验收**（覆盖核心闭环，不能只验证"程序能启动"）：

| 场景 | 验证内容 |
|---|---|
| S1 注册与角色 | 学生注册并以学生身份登录后，**看不到**"发布活动"入口；教师同理 |
| S2 发布与浏览 | 教师发布活动后，学生在列表中看到该活动，详情信息完整 |
| S3 报名约束 | 报名成功；重复报名被拒；满员后报名被拒；取消后可再报（活动仍在报名中时） |
| S4 名单查看 | 学生报名后，教师在名单中看到该学生，人数 +1 |
| S5 活动管理 | 教师取消活动后，学生端显示"已取消"且不能报名；已有报名记录保留 |
| S6 参与记录 | 学生能在"我的参与"中看到自己的报名历史 |
