# 校园活动管理系统 V1.0 — 工程意图

> **定位**：本文档是 V1.0 开发的总纲，回答"为什么做、做什么、不做什么、守什么规矩、怎么算做完"。后续的软件设计、编码和验证均以本文件为依据。若开发中发现原有理解存在问题，应先修订本文件，再修改软件。

---

## 一、为什么建设当前版本（Why）

1. **业务动机**：学校活动信息分散、报名管理低效，需要一个信息系统支撑"教师组织活动 — 学生参与活动"的基本业务，让活动信息有统一的发布与浏览入口，让报名有统一的记录与统计。
2. **工程动机**：作为课程实验的第一个迭代版本，以**最小可行版本**验证基本业务闭环能否成立，并建立"需求 → 设计 → 实现 → 验证"相互关联的工程意识，为后续迭代打基础。
3. **本版本不为**：不追求功能数量、代码规模或技术炫技；不以"看起来完整"为目标，而以"业务真正闭环"为目标。

## 二、当前版本主要解决什么问题（Problem）

| 问题 | 现状 | V1.0 方案 |
|---|---|---|
| 信息触达 | 活动靠海报、群通知，学生不知道有什么活动 | 教师统一发布，学生统一浏览（列表 + 详情） |
| 报名管理 | 报名靠表格、问卷，组织者难以统计 | 在线报名（含容量/重复校验），教师实时查看名单 |
| 参与记录 | 谁参加了什么活动，无据可查 | 报名记录持久化，学生可查"我的参与" |

## 三、本轮准备完成的内容（Scope）

**纳入范围**（来自《需求分析》评审确认的核心需求）：

| 编号 | 内容 |
|---|---|
| FR1 | 用户注册（账号、密码、姓名、角色：学生/教师） |
| FR2 | 用户登录 / 退出（按角色进入对应视图） |
| FR3 | 活动发布（教师：标题、简介、时间、地点、容量上限） |
| FR4 | 活动浏览（学生：列表 + 详情） |
| FR5 | 活动报名 / 取消报名（学生） |
| FR6 | 报名名单查看（教师） |
| FR7 | 活动管理（教师：编辑、取消、结束） |

同时落实业务规则 BR1–BR5（角色权限、状态约束、容量上限、防重复报名、取消/结束后关闭报名）和数据模型（用户表、活动表、报名记录表）。

**明确不做**（列入后续迭代候选，本版本不因"顺便"而扩大范围）：

- 系统管理员功能、教师身份审核
- 活动搜索筛选、签到、评价、消息通知、数据统计
- 高并发、分布式等非必需架构

## 四、软件实现需要遵守的重要约束（Constraints）

1. **时间**：2026 年 9 月 13 日 23:59 前提交；按里程碑分阶段推进，不做"最后一晚冲刺"。
2. **人员**：1～3 人小组，提交信息体现分工。
3. **技术栈**：Java 17 + Spring Boot 3 + Thymeleaf + Spring Data JPA + H2 + Maven。小组只学过 Java 语言基础，**实现以简单直接为先**，不引入超出理解范围的复杂技术；采用分层结构（Controller / Service / Repository），业务规则集中在 Service 层。
4. **安全**：密码使用 BCrypt 哈希存储；仓库中不提交密码、Token、密钥及真实个人隐私数据（.gitignore 保证）。
5. **已知简化**（显式声明，非遗漏）：注册时自选角色、不做教师身份审核；V1.0 单机运行、不做高并发。上述简化不影响基本业务闭环成立。
6. **过程规范**：Git 小步提交，提交信息用 `feat:` / `fix:` / `docs:` 等前缀说明修改内容；需求、设计、代码之间保持可追踪；**AI 生成内容属于候选工程成果，经小组检查确认后才能成为正式成果**；开发中发现问题先回到需求与工程意图重新判断，不直接按 AI 建议扩大或改变实现范围。

## 五、根据什么判断当前版本已经达到预期目标（Definition of Done）

**验收标准**：以下 6 个场景全部通过，即认定 V1.0 达到预期目标；任一场景失败，则定位原因、修复后重新验证受影响场景。

| 场景 | 验证内容 |
|---|---|
| S1 注册与角色 | 学生注册登录后看不到发布入口；教师可以看到 |
| S2 发布与浏览 | 教师发布活动后，学生能在列表和详情中看到完整信息 |
| S3 报名约束 | 重复报名被拒；满员后报名被拒；取消后可再报（活动仍在报名中） |
| S4 名单查看 | 学生报名后，教师名单中出现该学生，人数 +1 |
| S5 活动管理 | 教师取消活动后学生端显示已取消且不能报名；已有报名记录保留 |
| S6 参与记录 | 学生能在"我的参与"中看到自己的报名历史 |

验证不只判断"程序能否启动"，还包括业务过程是否按预期运行；验证结果记录入验证报告。

## 六、迭代里程碑（如何"慢慢做"）

每个里程碑独立提交、可验证，完成一个再进入下一个：

| 里程碑 | 内容 | 完成标志 |
|---|---|---|
| M1 | 项目骨架：pom、启动类、配置、H2 连通 | `mvn spring-boot:run` 启动成功，出欢迎页 |
| M2 | 用户模块：注册、登录、拦截器、角色视图 | 场景 S1 通过 |
| M3 | 活动模块：发布、列表、详情、管理 | 场景 S2、S5 通过 |
| M4 | 报名模块：报名/取消、校验规则、名单 | 场景 S3、S4、S6 通过 |
| M5 | 整体验证与修复：全场景走查、记录 | S1–S6 全部通过，形成验证记录 |

每个里程碑内部按功能小步提交（一个功能 1～3 次提交），提交信息对应需求编号（如 `feat: 完成活动发布（FR3）`），保证需求—代码可追踪。
