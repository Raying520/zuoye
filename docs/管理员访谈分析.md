# 校园活动管理系统 — 管理员访谈需求分析

> 访谈对象：系统管理员（平台运营与维护人员）  
> 访谈方式：开放式问答  
> 分析目的：从平台治理视角识别账号、权限、活动监管等方面的管理需求，为 V2.x / V3.0 迭代提供输入。

---

## 一、访谈核心信息提取

### 1.1 用户账号状态管理

| 管理员原话 | 解读 |
|---|---|
| “我可以查看平台里的用户账号和基本状态，确认账号是否处于正常使用状态。” | 管理员需要一个用户列表，能查看账号状态（正常 / 停用等）。 |
| “发现账号存在明显异常时，系统管理员可以停用；问题处理后，也可以恢复为可用状态。” | 管理员需要启用 / 停用账号的能力，作为风控与问题处理手段。 |

**现有 V1.0/V2.0 状态**：系统仅支持注册、登录与角色区分，没有账号启用/停用状态，也没有管理员视角的用户管理入口。

---

### 1.2 角色与权限边界

| 管理员原话 | 解读 |
|---|---|
| “平台里有学生用户、活动组织教师和系统管理员，不同角色能处理的事情不一样，我需要关注这些权限是否正常。” | 管理员需要确认三类角色（学生、教师、管理员）的权限按设计生效。 |
| “具体参加条件和报名审核由活动组织教师负责，这个问题建议问组织该活动的教师。” | 管理员不介入具体活动的业务审核，权限边界清晰。 |
| “具体人数由负责这个活动的教师根据实际组织条件确定，这属于活动组织规则，请询问活动组织教师。” | 容量、报名规则等属于教师自治范围，管理员不越权干预。 |

**现有 V1.0/V2.0 状态**：角色已在登录与 Controller 中通过 `User.Role` 区分，但缺少一个集中展示“谁拥有什么权限、是否越权操作”的管理面板。

---

### 1.3 平台活动信息监管

| 管理员原话 | 解读 |
|---|---|
| “我可以查看平台中的全部活动，用于监督是否有违规或明显错误的信息，但不会代替教师处理具体报名。” | 管理员需要一个只读/有限干预的平台活动监管视图。 |
| “活动不合规，是让他改还是你直接改？他不改怎么办？” | 当出现违规活动时，需要一套处理机制：通知整改、标记违规、下架/禁用活动等。 |

**现有 V1.0/V2.0 状态**：教师只能管理自己发布的活动，学生可以浏览/报名；管理员没有监管入口，也无法对违规活动进行处理。

---

## 二、管理员视角的缺口对照

| 需求点 | V2.0 支持情况 | 访谈中暴露的缺口 |
|---|---|---|
| 用户注册 / 登录 / 角色分流 | ✅ 已支持 | 缺少账号状态（启用/停用） |
| 教师发布 / 编辑 / 管理活动 | ✅ 已支持 | 缺少平台级监管视图 |
| 学生报名 / 取消 / 查看状态 | ✅ 已支持 | 管理员无法查看全局报名数据 |
| 账号启用 / 停用 | ❌ 未支持 | 核心缺口 |
| 用户列表 / 角色管理 | ❌ 未支持 | 核心缺口 |
| 平台活动监管 | ❌ 未支持 | 核心缺口 |
| 违规活动处理 | ❌ 未支持 | 核心缺口 |
| 操作日志 / 审计 | ❌ 未支持 | 访谈未直接提及，但与账号停用、活动下架等管理动作强相关 |

## 三、新增候选需求清单（供 V2.x / V3.0 评审）

### 3.1 功能需求

| 编号 | 需求 | 说明 | 建议阶段 |
|---|---|---|---|
| FR16 | 用户账号状态管理 | 管理员可查看用户列表，将账号置为“启用 / 停用”，停用的账号无法登录 | V3.0 |
| FR17 | 用户角色查看与核对 | 管理员可查看每个用户的角色（学生 / 教师 / 管理员）及注册时间 | V3.0 |
| FR18 | 平台活动监管视图 | 管理员可查看全部活动列表，按状态、发布者、关键词筛选 | V3.0 |
| FR19 | 违规活动处理 | 管理员可对违规或明显错误的活动标记为“待整改 / 已下架”，并通知发布教师 | V3.0 |
| FR20 | 操作日志 | 记录管理员的关键操作：账号停用/启用、活动下架/恢复、角色变更等 | V3.0 可选 |
| FR21 | 平台统计概览 | 管理员首页展示用户总数、活动总数、报名总数、待审核报名数等关键指标 | V3.0 可选 |

### 3.2 业务规则

| 编号 | 规则 | 说明 |
|---|---|---|
| BR12 | 管理员不替代教师处理报名 | 管理员只能监管活动信息，不能审核报名、修改名单或干预容量设置 |
| BR13 | 停用的账号禁止登录 | 账号状态为 DISABLED 时，登录应返回“账号已停用” |
| BR14 | 下架活动不可报名 | 被管理员下架的活动对学生隐藏或显示为“已下架”，不允许新报名 |
| BR15 | 下架不删除数据 | 管理员下架活动仅改变平台可见/可报名状态，不删除教师已发布的内容 |
| BR16 | 关键操作需留痕 | 账号停用/启用、活动下架/恢复必须记录操作人、时间、原因 |

### 3.3 数据状态扩展

| 状态 | 含义 | 适用对象 |
|---|---|---|
| ENABLED | 账号正常使用 | User |
| DISABLED | 账号被管理员停用 | User |
| NORMAL | 活动正常展示 | Activity（平台视角） |
| FLAGGED | 活动被标记待整改 | Activity |
| SUSPENDED | 活动被管理员下架 | Activity |

## 四、对现有系统的调整建议

### 4.1 数据表调整

1. **User 表**：
   - 新增字段 `status`（ENABLED / DISABLED），默认 ENABLED
   - 已有账号默认状态为 ENABLED

2. **Activity 表**：
   - 新增字段 `platform_status`（NORMAL / FLAGGED / SUSPENDED），默认 NORMAL
   - 与教师自管理的 `status`（OPEN/CLOSED/CANCELLED）正交，分别表示“教师业务状态”和“平台监管状态”

3. **新增 AdminOperationLog 表（可选）**：
   - `id`, `operator_id`, `operation_type`, `target_type`, `target_id`, `reason`, `create_time`

### 4.2 权限边界设计

```
学生：浏览活动、报名/取消、查看我的报名
教师：发布/编辑/结束/取消自己的活动、审核报名、查看名单
管理员：查看全部用户、启用/停用账号、查看全部活动、标记/下架违规活动、查看操作日志
```

### 4.3 流程调整

```
管理员发现违规活动
  → 查看活动详情（平台视角）
  → 选择“标记待整改”或“下架”
  → 填写处理原因
  → 系统自动通知发布教师（如支持消息通知）
  → 教师修改后申请恢复 / 管理员手动恢复
```

### 4.4 页面调整

| 页面 | 调整内容 |
|---|---|
| 管理员后台首页 | 展示平台统计卡片：用户数、活动数、报名数、待处理违规 |
| 用户管理页 | 列表展示用户名、角色、状态、注册时间；提供启用/停用按钮 |
| 活动监管页 | 列表展示全部活动，含发布者、状态、平台状态；提供查看/标记/下架按钮 |
| 操作日志页 | 展示管理员关键操作记录 |
| 登录页 | 账号停用时给出明确提示 |

## 五、V3.0 工程意图草案（五问）

| 问题 | 回答 |
|---|---|
| 为什么要做这一版？ | V2.0 解决了教师与学生之间的报名/审核/候补流程，但平台级治理（账号风控、违规活动监管）仍缺失。 |
| 解决什么问题？ | ① 异常账号无法被平台及时管控；② 违规/错误活动没有平台级处理入口；③ 管理员缺乏全局视图。 |
| 这一版做什么？ | 用户状态管理、平台活动监管、违规活动下架、管理员操作日志。 |
| 约束是什么？ | 管理员只监管不代管：不替代教师审核报名、不干预容量与名单；继续沿用 V2.0 技术栈。 |
| 怎么算完成？ | S13–S18 管理后台验收场景全部通过；V2.0 核心流程回归通过。 |

## 七、与教师访谈、学生访谈的交叉验证

| 维度 | 教师视角 | 学生视角 | 管理员视角 | 一致性 |
|---|---|---|---|---|
| 报名审核 | 教师按条件审核 | 希望状态透明 | 不越权，由教师负责 | ✅ 一致 |
| 活动信息修改 | 教师需要编辑 | 希望信息准确 | 只监管，不直接修改 | ✅ 一致 |
| 账号问题 | 未提及 | 未提及 | 需要启用/停用账号 | ⚠️ 新增缺口 |
| 违规活动 | 未提及 | 未提及 | 需要下架/标记 | ⚠️ 新增缺口 |
| 候补顺序 | 教师期望自动递补 | 学生希望知道位置 | 不干预具体规则 | ✅ 一致 |

**结论**：管理员访谈确认了“教师-学生”业务流程中权限边界设计的合理性，同时暴露了新缺口：**平台级账号监管**与**违规活动治理**。这两部分可作为 V3.0 的核心方向。
